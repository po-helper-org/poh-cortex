# Кортекс v2: разбор разрыва и план выпуска

Статус: разбор от 2026-09-22. Вход — `PAF_Product_Ops_guide_v22.docx` (методичка,
ред. 22), `poh-cortex-starter.zip` (эталонный скелет уровня 0) и текущее состояние
репозитория (`3c3e1a3`, ветка `claude/cortex-v2-po-agent-85uwp4`).

Цель v2, как её сформулировал человек: Кортекс должен работать **надёжной памятью
PO-агента при принятии решений о развитии продукта** и жить рядом с **Hermes Agent**
(профиль в Hermes). Ниже — что для этого есть, чего нет и в каком порядке это делать.

## 2. Главный вывод

Методичка описывает память решений как **четыре слоя с односторонним движением**
(раздел 14: «Поток → кандидаты → evidence → Нексус → ставки. Обратного движения нет»):

```
rules/      правила измерения        (лестница, гейты, распад)   — решения человека, без CP
evidence/   неизменяемые артефакты   (кто, когда, канал, ссылка, цитата, scope)
nexus/      узлы знания              (собраны из evidence, имеют срок годности)
bets/       обещания                 (порог CP + дата + зависимости + слабое звено)
```

**В poh-cortex v1 реализован только третий слой.** Нет `rules/`, `evidence/`, `bets/`,
`decisions/`, `log/`, `inbox.md`. Следствие — не косметическое:

- **CP назначается, а не выводится.** В v1 `confidence` — число 0..1, которое агент
  ставит по трёхстрочной прозаической шкале (`memory-protocol.md`, п.5). В методичке
  (раздел 9) CP **считывается с лестницы** ответом на один вопрос: какой самый сильный
  артефакт существует и открывается по ссылке. Разница принципиальная: в v1 число
  защищено только дисциплиной агента, в методичке — отсутствием артефакта.
- **Нет объекта, который несёт дату.** Узел Нексуса не отвечает на вопрос, ради
  которого PO держит память: «давать ли дату наружу». Между KR и эпиком в
  `ROADMAP/kr-epic-map.md` отсутствует ставка — единственный объект с порогом и сроком.
- **Память односторонняя: описан только контур записи.** `AGENTS.md` подробно
  регламентирует, как писать узел, и нигде не говорит, как память **читается при
  решении** и что агент обязан предъявить вместе с рекомендацией.

Отдельно: методичка перечисляет `poh-cortex-starter.zip` и `poh-cortex` как **два
разных материала** (раздел «Приложения»): стартер — «клонируемый скелет со всеми
правилами и командами», poh-cortex — «шаблон Кортекса: скиллы онбординга, гейт,
схема узла». v2 — это их объединение в один репозиторий, а не замена одного другим.

## 4. Целевая структура v2

```
AGENTS.md              контракт агента: + слой решений, + граница с Hermes
CLAUDE.md              точка входа
MINIMUM.md             ← новое: что делаете и чего НЕ делаете на уровне 0
VISION.md              стратегический слой человека
CHANGELOG.md           ← новое

rules/                 ← новое: правила измерения. Без CP. Меняются только на калибровке
  ladder.md            лестница 2–9: каркас фиксирован, формулировки организации
  gates.md             порог CP + дата по типам обещаний
  decay.md             change_rate по типам объектов, дефолт unknown = high
evidence/              ← новое: артефакты. Только добавление, правка = красный гейт
bets/                  ← новое: обещания с порогом, датой, зависимостями, cp_history
decisions/             ← новое: калибровки и решения квартала
log/                   ← новое: наблюдения без артефакта (латентность, тишина). На CP не влияют
_intake/               ← новое: единственная зона записи для Hermes
  inbox.md             быстрые вставки человека (3 строки: дата, кто и канал, цитата и ссылка)
  hermes/              выход ботов Hermes: кандидаты, черновики, наблюдения
GROUND/                без изменений по структуре
  config.yaml          + maturity_level, + agents (профиль Hermes)
  NEXUS/**             узлы знания + change_rate + authority
  PULSE/summaries/     эпизоды встреч
ROADMAP/kr-epic-map.md хребет OKR; между KR и эпиком появляется ставка
scripts/cortex.sh      + check (инварианты слоя решений), + cp, + daily, + equator
.claude/skills/        6 существующих + 9 из стартера + /paf-profile
```

Принцип разделения, который стоит удержать: **`GROUND/` — это то, что знаем.
`bets/`, `rules/`, `decisions/` — это то, что обещаем и чем меряем. `evidence/` —
то, чем это подтверждено.** Смешивать их в одном дереве не нужно: у них разные
жизненные циклы (узел стареет, артефакт — нет, правило меняется раз в квартал).

## 5. Развязка конфликта двух шкал CP

Это первое решение, которое надо принять: в v2 иначе окажутся две несовместимые
шкалы уверенности в одном репозитории.

| | v1 | Методичка |
|---|---|---|
| шкала | `confidence` 0.0–1.0 | ступень 2–9 |
| как получается | агент оценивает по прозе | считывается с лестницы по сильнейшему артефакту |
| потолки | нет | канал (устное ≤3), полномочия (не владелец ≤2), частота наблюдения (≤5) |
| распад | `ripeness` = ярлык, CP не трогает | `effective_CP = сила − распад(время × change_rate)` |

**Рекомендация.** Ступень 2–9 делается единственным *утверждаемым* числом,
`confidence` 0..1 остаётся полем движка и становится **производным**
(`confidence = cp / 9`), которое руками не правят. Тогда:

- Context Ripeness и отчёты движка продолжают считаться без его правки;
- 515 узлов рабочего vault остаются валидными (новые ключи движок игнорирует);
- гейт получает проверяемый инвариант: `confidence` не совпадает с `cp/9` → ERROR;
  `cp` выше ступени сильнейшего артефакта в `sources` → ERROR.

Новые ключи узла: `cp` (2–9), `change_rate` (`high|medium|low|unknown`), `authority`
(владелец объекта), `verified_at`, `scope`. Все — аддитивные, миграция не требуется.

## 6. Контракт с Hermes Agent

Методичка отводит этому отдельный раздел (П9) и формулирует правило архитектуры
жёстко: **уверенность считает только детерминированный агент по правилам из
`rules/`. Не Hermes и не OpenClaw.** Причина: самообучающийся агент меняет навыки по
опыту и через месяц начнёт считать иначе, чем договорились. Для рутины это
достоинство, для расчёта уверенности — дефект.

Отсюда разделение труда, которое v2 должен зафиксировать и в тексте, и в гейте:

| Слой | Кто | Куда пишет | Куда писать запрещено |
|---|---|---|---|
| Приём | OpenClaw (уровень 3) | `_intake/hermes/` | всё остальное |
| Сбор и подготовка | боты Hermes: Хранитель, Разборщик, Секретарь, Наблюдатель, Аналитик | `_intake/inbox.md`, `_intake/hermes/`, `log/`, черновики | `GROUND/NEXUS/`, `bets/`, `rules/`, `evidence/` |
| Расчёт и запись | PO-агент (Claude Code) по `rules/` | `evidence/`, `GROUND/NEXUS/`, `bets/` — **после подтверждения человека** | `rules/` без калибровки |
| Решение | человек | `rules/`, `decisions/`, VISION, даты наружу | — |

Что из этого делается машинно проверяемым (иначе правило живёт только в тексте):

1. **Поле `captured_by`** в каждом узле, evidence и ставке: `human` · `claude-code` ·
   `hermes:<бот>`. Гейт: значение `hermes:*` в `GROUND/NEXUS/`, `bets/`, `rules/`,
   `evidence/` → ERROR. Поток превращается в знание только через разбор.
2. **`intake_ref`** в evidence: ссылка на строку `_intake/`, из которой он вырос.
   Evidence без `intake_ref` и без ручного происхождения → WARN.
3. **Иммутабельность evidence**: `git diff` по `evidence/` показывает изменение
   существующего файла → ERROR. Артефакт можно добавить, нельзя переписать.
4. **Защита линейки**: `rules/*.md` изменены в одном коммите с `bets/*.md` → ERROR.
   Правила меняются отдельным коммитом с записью в `decisions/`. Это прямая защита от
   того, что самообучающийся агент подкрутит шкалу под нужный результат.
5. **Ограничение отправителей**: в `GROUND/config.yaml` — список ботов Hermes,
   которым разрешено писать в `_intake/`. Агент, доступный всем, исполняет чужие
   инструкции (это же требование в разделе «Корпоративная безопасность» П9).

Формат записи, который Hermes обязан отдавать в `_intake/` (он же формат Шага 7) —
три строки, и это должно быть описано схемой, чтобы навык Hermes её эмитил, а
PO-агент парсил детерминированно:

```
2026-09-17 | Петров, владелец БАЗИС | slack: <permalink>
"объём подтвердим к концу недели, схему отдадим после"
```

Порядок подключения из методички соблюсти буквально: **уровень 0–1 — только
Claude Code**; Hermes добавляется на втором квартале, когда правила устоялись.
«Агенты поверх неустоявшейся системы автоматизируют хаос».

## 7. Чего не хватает самому PO-агенту: контур чтения

Это разрыв, который не виден в структуре файлов, но определяет, будет ли память
использоваться. Сейчас `AGENTS.md` описывает только **запись**. Для решений нужны
ещё две вещи.

**Контур чтения перед решением.** Порядок обязательного чтения: `rules/` (по какой
шкале меряем) → `bets/` (какие обещания уже даны и на чём стоят) → узлы Нексуса по
теме вопроса → открытые вопросы и `wilting`-узлы. Решение, принятое без этого
порядка, опирается на случайную выборку памяти.

**Контракт ответа.** Любая продуктовая рекомендация агента заканчивается тремя
строками, иначе она неотличима от мнения:

- **на чём держится** — CP и конкретные файлы `evidence/`;
- **что неизвестно** — открытые вопросы и у кого они закрываются;
- **что изменит ответ** — какой минимальный артефакт поднял бы ступень.

Третья строка — самая ценная: она превращает ответ «не знаю» из тупика в задачу.

**Чего агент не решает** (раздел «Чего не делегировать никому», П9; в v1 близкая
таблица уже есть в `ops-model/delegation-boundary.md` — её надо дополнить):
обещания наружу, изменение правил, отправка сообщений от имени человека, переговоры
о датах и ёмкости, запись в узлы без подтверждения.

## 8. Гейт v2: инварианты

К существующим проверкам схемы добавляются проверки обоснованности. Это то, что
делает память «надёжной» в машинном, а не в декларативном смысле.

| Проверка | Severity |
|---|---|
| `cp` выше ступени сильнейшего артефакта в `sources` | ERROR |
| `cp` нарушает потолок канала (устное > 3) или полномочий (не владелец > 2) | ERROR |
| `confidence` ≠ `cp / 9` | ERROR |
| ставка: `cp_current` > минимума CP критических зависимостей (слабое звено) | ERROR |
| ставка: `cp_current` ниже порога гейта, а дата гейта прошла | ERROR |
| зависимость ставки без `owner` или без `channel` | ERROR |
| evidence без `scope`, `author`, `channel`, `date` или `link` | ERROR |
| изменён существующий файл в `evidence/` | ERROR |
| `captured_by: hermes:*` вне `_intake/` и `log/` | ERROR |
| `rules/` и `bets/` изменены одним коммитом | ERROR |
| узел `wilting` → `effective_cp` понижен автоматически, не молча оставлен | WARN → пересчёт |
| `change_rate: unknown` | WARN (трактуется как `high`) |
| ставка без движения CP больше двух недель | WARN |
| темпа роста CP не хватает до даты гейта | WARN (это вход в `/paf-equator`) |

Технически: `bets/`, `evidence/`, `rules/` лежат вне `GROUND/NEXUS/`, поэтому их
проверяет **собственный валидатор в `scripts/`**, а не движок. Это сознательно:
`node_type` в движке — закрытый enum, и заводить типы `bet`/`evidence` значит
тянуть PR в `poh-memory-engine` и связывать релиз v2 с релизом движка. Если позже
захочется видеть ставки в графе (ребро `satisfies` от ставки к KR даёт достижимость
цели «из коробки») — это отдельный инкремент с PR в движок, не блокер v2.

## 11. Совместимость и миграция

- **Рабочий vault `mts-po-workspace/GROUND` (515 узлов, 28 Нексусов) не ломается**:
  все новые ключи аддитивны, движок игнорирует незнакомые поля. Единственное, что
  потребует прохода, — простановка `cp` и `change_rate`; до этого узлы живут со
  старым `confidence`, а валидатор инвариантов их пропускает по признаку отсутствия `cp`.
- **Движок не меняется** на этапах P0–P1. Это сознательное ограничение: релиз v2 не
  должен зависеть от релиза второго репозитория.
- **Порядок для существующих пользователей**: сначала `/paf-rules` (лестница —
  условие, при котором всё остальное имеет смысл), затем `/paf-bet` по текущему
  кварталу, затем `/paf-cp`. Переразмечать 515 узлов задним числом не нужно и вредно:
  ступень ставится там, где есть артефакт, а не там, где есть узел.

## 12. Решения, которые остаются за человеком

По `AGENTS.md` §10 это не додумывается агентом:

1. **Одна шкала или две.** Принять `cp` 2–9 как единственную утверждаемую и сделать
   `confidence` производным — или оставить `confidence` ведущим и отказаться от
   лестницы. Второе означает отказ от механики методички.
2. **Где живут ставки** — в корне (как в стартере, без правки движка) или как узлы
   Нексуса (граф целиком, но PR в движок и связка релизов).
3. **Профиль реестра Нексусов** — оставить продуктовый канон PAF по умолчанию или
   добавить корпоративный профиль (IT-ландшафт, внешние зависимости, процессы,
   эксперименты) как альтернативный каталог.
4. **С какого уровня зрелости стартует шаблон** — сейчас v1 приносит CI с первого дня,
   методичка относит это к уровню 2.
5. **Когда подключается Hermes** — методичка говорит «со второго квартала». Если
   профиль Hermes уже работает, нужно решить, что он пишет **сегодня**, и зафиксировать
   это в `config.yaml` до того, как он начнёт писать хоть куда-то.

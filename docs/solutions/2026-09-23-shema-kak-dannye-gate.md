# Схема в коде ломала гейт — типы, рёбра и зоны стали данными

## Ситуация

Гейт целостности памяти на наполненном vault заваливал проверку: десятки узлов
отвергались только за «незнакомый тип». Добавить новый тип узла, объект управления
или агента означало правку кода инструмента — схема была зашита в движок
`poh-memory-engine`.

## Причина

Инструмент знал схему наперёд: типы, рёбра и правила жили в коде, а память растёт
быстрее кода — любое новое доменное понятие становилось для гейта ошибкой. Шум из
десятков ложных находок прятал реальные расхождения.

## Решение

Схема вынесена в данные репозитория — `GROUND/SCHEMA/`: `nodes.yaml`, `edges.yaml`,
`ladder.yaml`, `agents.yaml`, `profiles.yaml`, `gates.yaml`, `checks.yaml` (типы
узлов, рёбра, лестница доказательности, зоны агентов, профили распада, правила гейтов
и проверок). Инструмент читает их при каждом запуске и ничего не знает наперёд:
новый тип узла или агент — декларация в своём репозитории, а не правка кода и не PR
в чужой репозиторий. Ложные срабатывания ушли: остаются единицы находок, и каждая
указывает на реальное расхождение.

## Как проверить

Приёмка на чистом клоне с origin — 14 проверок, 0 провалов; дымовой тест — 29
проверок; гейт зелёный на наполненной памяти. Добавить новый тип узла декларацией в
`GROUND/SCHEMA/nodes.yaml` и убедиться, что гейт принимает его без правки кода.

## Уроки

- Проверочный инструмент, зашивший правила в код, сам становится источником шума:
  ложные срабатывания хоронят настоящие. Правила — в данные, рядом с памятью.
- «Незнакомый тип» — почти всегда не ошибка памяти, а отставание схемы.

# Кортекс и профили Hermes: организация данных и план работ

Исходная задача: в Hermes несколько профилей PO (GDS, Live, финтех, конверсия
витрины, партнёрские продажи). У каждого профиля своя память. Нужен один
Кортекс на всех — и понимание, что в нём общее, что своё и как это не
разъезжается.

---

## 1. «Константы против изменяющихся» — не та ось

Формулировка соблазнительная, но под ней склеены три разных вопроса, и
разделять память надо по ним, а не по «часто/редко меняется»:

| Вопрос | Чем отвечается | Где живёт |
|---|---|---|
| Кто владеет и кто вправе менять? | `scope` + `owner` | узел, Нексус |
| Как быстро протухает? | `change_rate` → `ttl_days` | узел |
| Кому это нужно часто? | подписка профиля | профиль, **не узел** |

Почему это важно практически.

**«Константа» — самое опасное слово в памяти организации.** Оргструктура
выглядит константой: департаменты, кто чем владеет, кто кому подчиняется. Но
человек ушёл три месяца назад — и пять профилей три месяца маршрутизируют
вопросы в пустоту, причём уверенно. Именно у «констант» не бывает регулярной
перепроверки, потому что их никто не считает изменяемыми.

В Кортексе поэтому **нет констант.** Есть узлы с низкой скоростью распада и
назначенным куратором: `change_rate: low` → `ttl_days: 90`, и через 90 дней
узел увядает и попадает в `cortex stale` к своему владельцу. Медленное знание
живёт дольше, но не вечно.

**Константность — свойство не данных, а отношения профиля к данным.** Витрина
для PO конверсии — объект ежедневных изменений; для PO финтеха — стабильная
внешняя система, о которой достаточно знать факт и владельца. Один и тот же
узел. Поэтому объективная частота изменений (`change_rate`) живёт на узле, а
субъективная «горячесть» — подписка профиля, и путать их нельзя: иначе PO
конверсии выставит витрине `high`, а PO финтеха получит ложную тревогу.

## 2. Три уровня памяти плюс поток

```
┌─ Ядро организации ────────────── scope: org ──────── меняется медленно, куратор один
│  люди, оргструктура, IT-ландшафт, интеграции, процессы,
│  стандарты и комплаенс, портфель продуктов
│  ⇒ одна копия на всех. Дублирование запрещено: пять версий одного
│    человека — это пять разных ответов на вопрос «кому писать»
│
├─ Зона PO ──────────────── scope: team:GDS | product:vitrina ─ меняется каждый спринт
│  цели и KR команды, ставки с датами, эксперименты и их итоги,
│  стратегия и приоритеты, решения квартала
│  ⇒ пишет свой PO, читают все. Чужая зона доступна на чтение всегда:
│    на этом и держится смысл общей памяти
│
├─ Поток ──────────────────── _intake/, PULSE/ ────── эфемерный, сгорает при разборе
│  выгрузки чатов, транскрипты, радары, дейлики, вставки из переписки
│  ⇒ у каждого профиля свой каталог. Знанием становится только после
│    разбора и вашего подтверждения
│
└─ Память профиля Hermes ───── вне Кортекса ──────── живёт в самом Hermes
   стиль общения, предпочтения этого PO, незакрытые ниточки разговора,
   выученные привычки профиля
   ⇒ в Кортекс не попадает никогда: это «как мне работать», а не
     «что известно об организации»
```

Последняя строка — главная граница. Память профиля Hermes самообучающаяся: она
меняется от опыта и через месяц становится другой. Кортекс курируемый: он
меняется только источником. Смешать их значит потерять свойство, ради которого
Кортекс существует — что его утверждение можно проверить.

### Чем уровни отличаются на практике

| | Ядро | Зона PO | Поток |
|---|---|---|---|
| пример | «Николаев — директор билетного бизнеса» | «KR 2.3 квартала GDS» | сообщение в чате |
| владелец | организация, назначенный куратор | конкретный PO | никто |
| `change_rate` | low / medium | medium / high | — |
| `ttl_days` | 90–180 | 21–42 | сгорает |
| кто пишет | куратор ядра | свой PO | сборщики, боты Hermes |
| чужой PO | читает, не пишет | читает, не пишет | не видит |
| при конфликте | решает куратор | решает владелец зоны | конфликта не бывает |
| дублирование между профилями | **запрещено** | естественно | естественно |
| что ломается без разделения | пять версий одного человека | PO Live правит цели PO GDS | шум попадает в знание |

## 3. Физически: одно хранилище, срез на профиль

**Хранилище одно.** Пять репозиториев дают изоляцию, но убивают то, ради чего
всё затевалось: общий словарь. Когда PO GDS выяснил, кто владелец билетного
бизнеса, PO Live не должен выяснять это заново — иначе через квартал у вас пять
несопоставимых онтологий одной компании.

**Доставка — срез.** Профиль получает не весь репозиторий, а собранный пакет:
ядро + своя зона + подписки + открытые вопросы. Это решает сразу две вещи:

- **вопрос доступа перестаёт быть блокирующим.** Есть у профиля шелл или нет,
  файл он прочитает в любом случае. Исполнение нужно только детерминированному
  прогону, который один на всех;
- **срез помещается в контекст.** 500 узлов целиком профилю не нужны и не
  влезут; его зона плюс ядро — влезут.

```
        одно хранилище (git)
                │
   детерминированный прогон: gate · refresh · сборка срезов
                │
   ┌────────────┼────────────┬─────────────┐
   ▼            ▼            ▼             ▼
профиль GDS  профиль Live  профиль финтех  …
читает срез  читает срез   читает срез
пишет в      пишет в       пишет в
_intake/gds  _intake/live  _intake/fintech
```

Конфликты записи почти исключены: очередь — отдельный каталог на профиль,
курируемая запись сериализуется через детерминированный прогон и вашу приёмку.

## 4. Что уже готово, а чего нет

Честная граница, чтобы план не переделывал сделанное.

| | Состояние |
|---|---|
| `scope` на узле и Нексусе, наследование от Нексуса | **есть** |
| фильтрация чтения по зоне (`ask --scope`, `context --scope`) | **есть** |
| зоны записи агентов по путям + проверка гейтом | **есть** |
| `change_rate` → `ttl` → распад CP → `stale` | **есть** |
| очередь `_intake/` и контракт формата | **есть** |
| запрет писать в чужую зону и в ядро | **есть** (P0): считается по `scope`, пересечение легализуется через `shared_with` |
| идентичность профиля | **есть** (P0): `CORTEX_PROFILE` / `--as`, реестр `profiles` в `SCHEMA/agents.yaml` |
| машинный вход для не-Claude-Code агента | **есть** (P0): `ONBOARDING.md` |
| онбординг как процедура, а не слэш-команда | **есть** (P0): протокол в `ONBOARDING.md`, записи идут черновиками |
| очередь приёмки | **есть** (P0): `cortex review`, пачкой по Нексусу и поштучно |
| резолвер упоминаний | **есть** (P0): `cortex resolve`, поле `aliases` |
| кураторство ядра | **есть** (P0): `core.curator` в схеме + `CODEOWNERS`, изменения ядра через PR |
| подписки профиля | **есть** (P1): `subscriptions`, в том числе на Нексус целиком |
| сборка среза на профиль | **есть** (P1): `cortex pack`, `--all`, свежесть проверяется в CI |
| отчёт по стыкам между PO | **есть** (P1): `cortex seams`, сортировка по слабому звену |

## 5. План работ

### P0 — профиль проходит онбординг без вас в роли переводчика ✅ сделано

Закрывает ваш HowToDemo целиком. Реализовано; ниже — что именно.

1. **Машинный вход.** `ONBOARDING.md` в корне: «ты агент профиля, вот твоя
   зона, вот порядок действий, вот чем подтверждать». Без зависимости от
   `.claude/skills/`. Claude Code продолжает читать `CLAUDE.md`, остальные —
   этот файл.
2. **Идентичность профиля.** `CORTEX_PROFILE=po-gds` (или `--as`), реестр
   профилей в `SCHEMA/agents.yaml` с их `scope`. Отсюда автоматически:
   `captured_by`, зона по умолчанию при записи, каталог очереди
   `_intake/<профиль>/`.
3. **Запрет на чужую зону.** Зона агента считается по `scope`, а не по путям:
   запись в `team:Live` от профиля GDS — ERROR гейта. Ядро (`scope: org`)
   пишет только куратор.
4. **Онбординг как процедура.** Тот же интервью-протокол, но: кладёт узлы
   черновиками (`status: draft`) в зону профиля, не трогает ядро, на выходе
   даёт вам список на приёмку.
5. **Очередь приёмки.** `cortex review` — что собрано и ждёт подтверждения;
   `cortex review --accept <id>` / `--reject <id>`. Черновик без приёмки не
   участвует в ответах как факт (это ваш шаг 5).
6. **Резолвер.** `cortex resolve "Николаев"` → узел персоны с ролью, зоной и
   ступенью; `cortex resolve "витрина"` → система и её владелец. Это ваш шаг 6:
   агент понимает, о ком и о чём вы говорите.

**Критерий готовности:** вы отдаёте ссылку профилю PO GDS, он проходит
онбординг, вы принимаете 20–40 узлов через `review`, после чего он отвечает на
«что у нас с витриной» с якорями и не путает её с чужой системой.

### P1 — пять профилей живут в одной памяти, не мешая друг другу ✅ сделано

7. **Срез на профиль.** `cortex pack --profile po-gds` → один markdown:
   ядро + своя зона + подписки + открытые вопросы + протухшее. Пересобирается
   детерминированным прогоном, кладётся туда, откуда профиль читает.
8. **Подписки.** `subscriptions: [system-vitrina, team-nikolaev]` у профиля:
   что из ядра для него горячее. Влияет на срез и на то, чьё увядание ему
   показывается как срочное.
9. **Кураторство ядра.** Явный владелец у каждого Нексуса `scope: org` и
   регламент: увядший узел ядра — задача куратора, а не «ничья». Без этого
   ядро протухнет первым, потому что оно ничьё.
10. **Стыки между PO.** Отчёт «зависимости моей зоны от чужих»: когда ставка
    GDS упирается в систему, которой владеет команда Live. Это то, что сейчас
    живёт в переписке и теряется.

**Проверено на сценарии двух профилей с пересекающимися зонами:** узел GDS
зависит от узла Live и опирается на систему ядра; `seams` показывает у GDS оба
стыка, отсортированных по слабому звену (CP 3 на стороне Live), а у Live —
входящую зависимость с предупреждением, что понижение CP ударит по чужому
кварталу. Срез на реальном объёме (506 узлов, подписка на два Нексуса) — 37 КБ,
`--core-limit` его сжимает.

### P2 — эксплуатация ✅ сделано

11. **Регламент** — [docs/operating-rhythm.md](operating-rhythm.md) плюс
    `cortex agenda`: ритм стал исполняемым, а не абзацем. Порог просрочки
    очереди настраивается; пустая повестка — нормальный исход дня.
12. **Расхождения между зонами** — `cortex conflicts` находит пары узлов об
    одном объекте (по псевдонимам и заголовкам) из разных зон или от разных
    авторов, показывает обе стороны с источниками и **не выбирает**. `--mark`
    ограничивает уверенность обеих сторон потолком спора; снять можно только
    новым источником.
13. **CI** — гейт, `refresh --dry-run`, свежесть срезов, дымовой тест.
14. **Калибровка** — `cortex calibrate`: срок годности против наблюдаемой
    частоты изменений (по истории git, без онбординговой суеты и технических
    коммитов), лестница против исходов закрытых ставок, слепые зоны. Правки в
    правила вносит человек отдельным коммитом.

## 6. Решения, принятые человеком

1. **Зоны пересекаются.** Продукт сильносвязный, одна цель обычно требует
   координации нескольких PO. Поэтому `writes` у профиля — список, а
   пересечение на конкретном узле оформляется полем `shared_with`. Запись в
   чужую зону не запрещена наглухо — она требует явного соглашения, видимого
   в памяти, а не в переписке.
2. **Куратор ядра — один ответственный.** Принимает изменения по качеству,
   день ко дню, через PR. Закреплено в `SCHEMA/agents.yaml` (`core.curator`)
   и в `.github/CODEOWNERS`.
3. **Приёмка: онбординг пачкой, люди поштучно.** `cortex review --accept-all`
   работает только вместе с `--nexus`, а Нексус `team` в подсказке помечен как
   «смотрите поштучно»: ошибка в сегменте видна сразу, ошибка в том, кто чем
   владеет, всплывёт через месяц на неверно отправленном вопросе.

## 7. Что осталось решить

1. **Как профиль физически достаёт срез** — файл в шаре, git pull, HTTP.
   От этого зависит только пункт 7 (сборка среза), остальное уже не меняется.
2. **Имена зон.** Сейчас в схеме `team:GDS` и `team:Live` как образцы. Там, где
   двое пишут про один продукт (конверсия витрины и GDS), зона должна быть
   `product:vitrina` у обоих — иначе придётся на каждый узел вешать
   `shared_with`.

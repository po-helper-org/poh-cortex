# Кортекс как память экосистемы po-helper: что доработать

> **Этот документ — разбор, на основании которого сделана v2.**
> Реализация описана в [CHANGELOG.md](../CHANGELOG.md), путь переноса —
> в [migration-v2.md](migration-v2.md). Часть выводов ниже про движок
> `poh-memory-engine` неактуальна: зависимость от него снята целиком.

Статус: разбор от 2026-09-22, ветка `claude/cortex-v2-po-agent-85uwp4`.
Парный документ — [`v2-plan.md`](v2-plan.md): там слой решений (ставки, лестница,
evidence, Hermes). Здесь — другой вопрос: что должно измениться в Кортексе, чтобы
им пользовалась **экосистема ИИ-агентов po-helper** (45 навыков, 25 из которых
пишут в память), а не один человек с одним агентом.

Разница существенная. Память одного PO защищена его дисциплиной. Память роя
агентов защищена только контрактом: то, что не проверяется машинно, разъезжается
за квартал — и ниже это видно на числах.

---

## 1. Что проверено фактически

Гейт шаблона прогнан против рабочего vault `mts-po-workspace/GROUND` (422 узла
с frontmatter, 26 Нексусов, 25 пишущих навыков).

| Проверка | Результат |
|---|---|
| структура `config.yaml` + реестр | OK |
| **узлы** | **66 ERROR, 240 WARN** |
| дисциплина Node schema | 422 из 422 узлов несут все 10 обязательных ключей — правило соблюдается |
| `node_type` вне enum движка | **58**: `chat-profile` × 57, `process` × 1 |
| Нексусы вне `_registry.yaml` | **5**: `channels`, `compliance`, `project-management`, `requester-domain`, `system-landscape` — папки с узлами есть, регистрации нет |
| висячие рёбра | 3 |
| дрейф `ripeness` | **231 из 422** — заявленное значение не совпадает с вычисленным |
| узлов `wilting` | 4 |
| пустой `sources` | 5 (MOC-заглушки) |

Читается это так: **дисциплина у авторов есть, контракта нет.** Агенты честно
заполняют обязательные поля, но схема шаблона уже того, что они пишут, реестр
отстаёт от диска, а `ripeness` пишется один раз и не пересчитывается — то есть
метрика свежести, ради которой существует спелость контекста, в рабочей памяти
мертва больше чем наполовину.

## 2. Шесть находок

**F1. Гейт шаблона не проходит на рабочей памяти.** 66 ERROR. Значит `poh-cortex`
сегодня нельзя объявить подложкой po-helper: первый же прогон в CI будет красным,
а красный гейт, который все привыкли игнорировать, хуже отсутствующего.

**F2. Шаблон не знает о половине дерева, в которое пишут агенты.** В рабочем vault
живут и используются каталоги, которых в шаблоне нет вообще:

| Путь | Кто пишет |
|---|---|
| `GROUND/_intake/chats/`, `_intake/transcripts/`, `_intake/unrouted/` | `chat-sync`, `transcript-sync`, `confluence-indexator` |
| `GROUND/PULSE/radar/` | `link-radar` → `radar-promote` |
| `GROUND/PULSE/daybook/`, `PULSE/meetings/` | `daily-review`, `summary` |
| `GROUND/_index/risk-queue` | `risks --materialize` |
| `GROUND/NEXUS/_map` | `people-map`, навигация |
| `GROUND/NEXUS/team/_calibration/<run_id>/` | `nexus-calibration` |
| `GROUND/BUNCH/`, `GROUND/RESULTS/` | `sprint-planner`, отчёты спринта |

**F3. Контракт узла размазан по навыкам.** 25 навыков несут собственные
`resources/*.md` с правилами. `radar-promote` формулирует это прямым текстом:
«frontmatter-ключи **по образцу существующих**». Единого места, откуда навык берёт
правила записи, нет — поэтому дрейф из F1 не аномалия, а закономерный исход.

**F4. Шаблон использует собственный движок на треть.** `poh-memory-engine` — это
два яруса:

| Ярус | Пакет | Что умеет | Экспонирован в `cortex.sh`? |
|---|---|---|---|
| markdown (истина) | `paf_index` | деривация рёбер, гейт, отчёты, достижимость | да: `gate`, `report`, `gaps`, `build` |
| граф + вектор | `poh_memory` | claim-слой (битемпоральность, противоречия, вытеснение), риски, impact-дельта, reflexion, retrieval `text_to_replica` / `kr_to_replica` | **нет** |

Навыки po-helper зовут второй ярус вручную:
`PYTHONPATH=. ~/.cache/poh-venv/bin/python -c "..."`, знают внутренние сигнатуры
(в `poh-report` прямо написано «порядок аргументов РАЗНЫЙ — не перепутай»), сами
поднимают FalkorDB, сами создают и чистят scratch-графы и временный git-worktree.
Это не API, это склейка, и каждый новый навык копирует её заново.

**F5. Коллизия имён навыков.** `paf-onboard` и `paf-nexus-create` существуют в обоих
репозиториях в разных версиях (157 против 72 строк и 147 против 42). В одной сессии
(как сейчас, когда подключены оба репозитория) неоднозначно, какая сработает.

**F6. Нет контракта чтения.** Ни один из 45 навыков не имеет общего способа спросить
память «что известно про X и чем подтверждено». `po-agent`, `po-research`, `bft-*`
собирают контекст каждый по-своему — то есть отвечают из разной выборки одной и той
же памяти.

## 4. Три контракта, которых не хватает

Вся доработка сводится к тому, чтобы Кортекс перестал быть набором правил в прозе
и стал **интерфейсом с тремя входами**. Правило: то, что агент делает часто,
должно быть командой, а не абзацем инструкции, который он может прочитать иначе.

### 4.1. Контракт записи (Write API)

```
cortex.sh node add    --nexus <slug> --type <t> --id <node_id> --source <...> [--dry-run]
cortex.sh node update --id <node_id> --append-source <...> [--set cp=<n>]
cortex.sh node check  --id <node_id>          # валидация до записи, а не после
```

Что это закрывает: правила Node schema перестают копироваться в навыки (F3, п.4).
Навык вызывает команду, команда владеет схемой. Проверки, которые уезжают из прозы
в код: дедуп `node_id` и похожих заголовков (п.9), обязательный источник, additive
для curated-полей (п.10), автоматический `updated` и пересчёт `ripeness` (п.3),
провенанс `captured_by: skill:<имя>` и `intake_ref` (п.8).

`--dry-run` обязателен: половина навыков работает через ревью-гейт PO
(«сухой прогон → ок PO → запись»), и это должно поддерживаться интерфейсом, а не
воспроизводиться каждым навыком заново.

### 4.2. Контракт чтения (Read API)

```
cortex.sh ask     "<вопрос>"  --json     # text_to_replica + якоря
cortex.sh context --kr PO-43  --json     # kr_to_replica: что известно по цели
cortex.sh context --node <id> --depth 2  # окрестность узла
cortex.sh open-questions [--nexus <slug>] # что неизвестно и у кого закрывается
cortex.sh stale   [--nexus <slug>]        # wilting + дрейф, очередь верификации
```

Что это закрывает: F6 и п.5–6. Все навыки-потребители (`po-agent`, `po-research`,
`bft-*`, `request-intake`, `sprint-planner`) получают один вход и одинаковую выборку.
Выход — JSON с якорями (`node_id`, эпизод, источник), чтобы навык мог процитировать
происхождение, а не пересказать.

Внутри это тонкая обёртка над уже существующими `poh_memory.query.text_to_replica` /
`kr_to_replica` / `insight.analyze`. Писать нечего — надо экспонировать.

### 4.3. Контракт очереди (Intake API)

```
_intake/<источник>/    единственная зона, куда пишут неразобранное
cortex.sh intake list  что лежит и откуда
cortex.sh intake route разбор в кандидаты; запись — только через Write API
```

Что это закрывает: п.7 и стык с планом `v2-plan.md`. Сегодня `_intake/` фактически
используется (`chat-sync`, `transcript-sync`, `confluence-indexator`), но шаблоном
не описан, и правила у каждого поставщика свои. Это же единственная зона записи для
Hermes Agent — то есть контракт нужен один на всех поставщиков потока, внешних и
внутренних.

## 5. Расширяемость схемы: без этого рой ломает гейт

Корень F1 — `NODE_TYPES` захардкожен в `sa_documentation/validate_ground.py`.
Каждый новый навык, которому нужен свой тип узла (`chat-profile` у `info-channels`,
`process` у ops-model), либо роняет гейт, либо требует PR в движок.

**Решение: типы узлов объявляются в реестре, а не в коде движка.**

```yaml
# GROUND/NEXUS/_registry.yaml
- slug: channels
  source: custom
  node_types: [chat-profile, channel]     # ← объявляется здесь
  owner: Product Ops
```

Гейт валидирует `node_type` против объединения базового каталога PAF и типов,
объявленных в реестре. Тогда:

- новый навык расширяет схему декларацией, а не правкой чужого репозитория;
- расширение остаётся видимым и ревьюируемым — тип, которого нет в реестре,
  по-прежнему ERROR, так что защита от опечатки сохраняется;
- 58 сегодняшних ошибок закрываются двумя строками в реестре.

Парно к этому — **сверка реестра с диском** (п.2): папка `GROUND/NEXUS/<slug>/`
с узлами, не объявленная в реестре, должна быть ERROR с подсказкой
`/paf-nexus-create`, а не выявляться косвенно через узлы.

## 6. Дисциплина свежести

231 узел с дрейфом `ripeness` — это не 231 ошибка авторов, а отсутствующая команда.
`ripeness` объявлено вычисляемым (`p = (сегодня − updated) / ttl_days`), но
вычислять его некому: агент пишет значение в момент создания узла, и дальше оно
устаревает вместе с файлом.

Что делать:

1. `cortex.sh refresh` — пересчёт `ripeness` по всему vault, идемпотентно, отдельным
   коммитом. Это техническая операция, она не трогает `confidence`.
2. Гейт перестаёт считать дрейф предупреждением и начинает считать его **состоянием
   до `refresh`**: расхождение вычисляемого поля — не мнение автора, а несделанный
   пересчёт.
3. `cortex.sh stale` — очередь верификации: что протухло, у какого Нексуса владелец,
   что из этого подпирает активные цели квартала. Без очереди `wilting` остаётся
   ярлыком, который никто не разгребает.

Связка с планом решений: в `v2-plan.md` распад должен ронять CP ставок. Механика
пересчёта — общая, поэтому `refresh` стоит делать один раз и сразу под обе задачи.

## 7. Разделение ответственности репозиториев

Сегодня граница размыта, отсюда F5. Предлагаемая:

| Репозиторий | Что в нём живёт | Чего в нём не должно быть |
|---|---|---|
| `poh-memory-engine` | оба яруса движка, схема, валидатор | знания организации |
| `poh-cortex` | **подложка**: контракты записи/чтения/очереди, Node schema, гейт, `cortex.sh`, скиллы работы с памятью (`paf-*`) | доменные навыки продукта (БФТ, спринты, OKR-питч) |
| `mts-po-workspace` | рабочий vault + доменные навыки + интеграции (MTS.Link, Confluence, JIRA) | собственная копия правил Node schema |

Из этого следуют два действия:

- **Пространство имён.** Навыки подложки получают префикс, который не пересекается
  с рабочими: `cortex-*` для команд памяти, `paf-*` оставить за методологией.
  Либо — раз в обоих репозиториях есть `paf-onboard` и `paf-nexus-create` — свести
  их к одной версии, живущей в подложке, и удалить форк из рабочего репозитория.
- **Направление зависимости — одностороннее.** Рабочий репозиторий знает про
  подложку, подложка про рабочий — нет. Сейчас в шаблоне уже просачиваются детали
  конкретного развёртывания, и это надо остановить до релиза v2.

## 8. Гейт для роя

К проверкам схемы добавляются проверки, специфичные для многоагентной записи.
Каждая отвечает на вопрос «что сломается, если писать будут пятеро одновременно».

| Проверка | Зачем | Severity |
|---|---|---|
| `node_type` вне базового каталога и вне `node_types` реестра | защита от опечатки при свободном расширении | ERROR |
| папка Нексуса с узлами не объявлена в реестре | дрейф реестра (5 случаев сегодня) | ERROR |
| два узла с похожим заголовком в одном Нексусе | дубликат вместо обновления | WARN |
| узел без `captured_by` | не видно, какой навык его создал | WARN |
| curated-поле перезаписано, а не дополнено | additive-дисциплина `radar-promote` | ERROR |
| `ripeness` ≠ вычисленному | несделанный `refresh` | ERROR после ввода `refresh` |
| `sources` ссылается на несуществующий файл `_intake/` или `PULSE/` | битый якорь | ERROR |
| узел создан навыком, но не достижим от хребта KR | запись, не привязанная к целям | WARN |

Последняя — прямое продолжение `gaps`: у роя главный способ испортить память не
ложь, а накопление технически валидных узлов, которые ни на что не влияют.

## 9. Бутстрап окружения

Навыки `poh-report`, `risks`, `reflexion` требуют venv `~/.cache/poh-venv` и
поднятого FalkorDB, но ставит это сегодня человек руками. В подложке должно быть:

```
cortex.sh env up      venv + зависимости [graph] + FalkorDB, идемпотентно
cortex.sh env status  что доступно: markdown-ярус / граф / вектор
```

и явная деградация: без графа markdown-ярус (`gate`, `report`, `gaps`, `build`,
Write API) работает полностью, Read API отвечает «граф не поднят», а не падает
трассировкой. Это не удобство — при рое навыков непонятный отказ одного модуля
читается как «память сломана».

## 10. План по этапам

**Этап A — перестать ломать рабочую память (закрывает F1, F2).**
Типы узлов из реестра · сверка реестра с диском · `cortex.sh refresh` ·
описание фактически используемых каталогов (`_intake/`, `PULSE/radar/`, `daybook/`,
`_index/risk-queue`, `_map`, `BUNCH/`, `RESULTS/`) в схеме и шаблоне.
*Критерий готовности:* гейт шаблона зелёный на `mts-po-workspace/GROUND` без правки
контента узлов — только реестр и `refresh`.

**Этап B — три контракта (закрывает F3, F4, F6).**
Write API с `--dry-run` и провенансом · Read API поверх `poh_memory.query` ·
Intake API · `cortex.sh env up/status`.
*Критерий готовности:* `radar-promote`, `confluence-indexator` и `extract-claims`
переписаны на Write API и их локальные копии правил Node schema удалены; `po-agent`
и `po-research` собирают контекст через Read API.

**Этап C — граница и гарантии (закрывает F5, п.14–16).**
Пространство имён навыков и устранение форков · перенос правил Node schema из
рабочего репозитория в подложку · фикстура vault и контрактные тесты навыков ·
проверки роя в CI.
*Критерий готовности:* навык, нарушающий контракт записи, падает на тесте до
попадания в рабочий vault.

Порядок обязателен: контракты (B) поверх несходящейся схемы (A) закрепят дрейф,
а не устранят его.

## 11. Как это стыкуется с планом слоя решений

Два документа описывают разные оси одного релиза:

| | `v2-plan.md` | этот документ |
|---|---|---|
| вопрос | на чём агент обосновывает решение | как рой агентов не портит память |
| добавляет | `rules/`, `evidence/`, `bets/`, лестницу CP, контракт с Hermes | контракты записи/чтения/очереди, расширяемую схему, `refresh` |
| общее | `_intake/` как единственная зона неразобранного · провенанс записи · механика распада · гейт как место, где правило становится проверяемым |

Пересечений по файлам мало, поэтому это либо один релиз v2 с двумя ветками работ,
либо два: **сначала этот** (без него рой продолжит расходиться), потом слой решений.
Рекомендую второе: этап A даёт зелёный гейт на реальной памяти за несколько часов и
сразу окупается, а слой решений требует интервью с человеком (`/paf-rules`) и
календарного квартала на калибровку.

1. **Где живёт валидатор.** Типы из реестра требуют правки `validate_ground.py` в
   `poh-memory-engine` — или собственного валидатора в подложке поверх движка.
   Первое честнее, второе развязывает релизы.
2. **Судьба форков навыков.** `paf-onboard` и `paf-nexus-create` в рабочем
   репозитории длиннее и, вероятно, живее шаблонных. Сводить к версии подложки или
   поднять рабочие версии в подложку как основные?
3. **Обязательность графового яруса.** Read API на `poh_memory` означает, что
   FalkorDB становится зависимостью для части навыков. Держать его опциональным
   (с деградацией) или сделать обязательным для развёртывания po-helper?
4. **Кто владеет доменными навыками.** Если подложка не содержит БФТ, спринты и
   OKR-питч — они остаются в рабочем репозитории у одной команды или выносятся в
   третий, переиспользуемый?
5. **Что делать с 231 дрейфом прямо сейчас.** `refresh` одним коммитом по всему
   vault — операция техническая, но она трогает 231 файл и перекроет историю
   `git log` по ним. Делать до этапа A или вместе с ним?
